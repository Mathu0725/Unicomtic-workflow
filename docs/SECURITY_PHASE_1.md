# Security phase 1 — 26 October 2026

This phase upgrades the dependency stack and verifies candidate ownership before exposing admissions progress or accepting applications. Existing admissions data, integration credentials, mail allowance and saved form content are preserved. No production deployment or live candidate/provider write was performed for validation.

## Candidate experience

- Public registration remains form → thank-you. No student account or dashboard is added to that flow.
- `/status`, `/apply` and custom application/workshop forms first check the candidate's verified session. Otherwise, they ask for the registration reference and registered email address.
- A matching request queues an email through the existing outbox. Matching, unknown and throttled requests show the same generic response; the request response does not reveal whether a candidate exists.
- The email's secure link expires 30 minutes after dispatch. Opening it exchanges it for a one-hour HttpOnly, SameSite=Lax cookie, with Secure enabled in production. The token is carried in the URL fragment and removed from the address bar before exchange.
- Each link and session identifies a specific registration, student and keyed hash of the current email. An email correction or cancellation invalidates earlier access. Link and session tokens have separate authenticated types; a staff cookie cannot act as candidate proof.
- Links can be reopened during their validity window. They are not single-use tokens. A fresh request is required after expiry.
- Existing confirmation emails generated by the worker have same-origin status/application links upgraded at dispatch, only when the recipient is the candidate's registered address. Previously delivered plain reference links open the verification gate.

## Server enforcement

- The status API rejects bare reference/NIC lookups with HTTP 401. A verified candidate can view only their own registration; requesting another reference or using a NIC query is refused.
- Both application APIs require verified access, a matching intake and an invited/applied registration. Custom form answers must resolve to the verified student before duplicate/submission responses are produced.
- Authorization runs before retry-receipt lookup. Candidate retry receipts are scoped to the verified registration, preventing another verified candidate from replaying a receipt with a copied key and request body.
- Application/workshop document uploads require verified access before any Drive call. Application uploads also require an invitation. Upload retry identifiers and document receipts are bound to the verified registration and cannot be attached by another candidate. Old unbound application uploads must be uploaded again.
- Registration-form uploads retain the existing public registration flow, file validation and receipt checks.
- Secure-link requests use durable, keyed-hash attempt buckets in the existing platform aggregate: 100 requests per source per 15 minutes and three matching requests per reference per hour. Invalid email matches do not consume the per-reference allowance. Pending access emails are deduplicated. Exchange is limited to 20 successful exchanges per registration per 15 minutes.
- Without `TRUST_PROXY=true`, request throttling uses a shared direct-source bucket. Set that flag only behind a trusted proxy that replaces client-supplied forwarding headers. The existing process burst limiter and bounded request body also remain active.
- Secure-link emails use the normal rolling 24-hour sending budget. Tokens are generated when the worker dispatches the email, so a queue/quota delay does not expire an already-created token.
- Responses include same-origin referrer policy, frame protection, content-type sniffing protection and restricted device permissions.

The new attempt buckets and optional document ownership metadata hydrate compatibly in the existing JSON platform state. This phase does not require a SQL migration or change Supabase grants, keys or integration secrets.

## Running and follow-up

Use `npm ci`, `npm test`, `npm run typecheck`, `npm run build` and `npm run dev` with Node 24+. Production requires HTTPS, a stable 32-character-or-longer `APP_SECRET`, the existing administrator configuration and the correct `NEXT_PUBLIC_APP_URL`. Changing the app secret also affects encrypted saved integration credentials; do not rotate it casually.

Secure-link email delivery requires the existing notification worker, just like other queued emails. The live worker remains stopped/stale during this change; running a worker can dispatch real queued candidate messages and scheduled workshop reminders. Persistent worker supervision and recovery are the next operational phase. No live messages were sent to validate these changes.

Staff disable/reset/session revocation, automatic backups/restore drills, the single-course/intake cleanup and the other items in the [project review](PROJECT_REVIEW_2026-10-26.md) remain pending.

On this workstation, `DISABLE_BUILD_CACHE=true` disables regenerable Webpack caching to fit the available C: drive space. Only build/package caches were cleaned; admissions records and backups were retained.
